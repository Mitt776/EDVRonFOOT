# Design

## Context

Мотив — в proposal.md (Why). Что уже известно (исследование, «Прогулка `.16`»; декомпиляция `0x58F940` и `0x58F7D0` в
scratchpad `2625e5da…\scratchpad\re\m1.c`, `m2.c`):

```
// 0x58F940(node) — подготовка узла, зовётся из 0x58B090 до рисования узла
ctx = *(*(node+0x108)+0x60);  cam = node+0x100
ctx+0x150 = node;  ctx+0x158 = cam                        // всегда
if (node+0xD8 == 0 || byte node+0x250 != 0) {
    ctx+0x250 = cam;  ctx+0x258 = node+0x108
    L = *(ctx+0x108)                                      // L[0] — массив указателей, (u32)L[1] — их число
    for i < L[1]: p = L[0][i]; if (p) p+0x30 = (p+0x28 & cam+0x8E0) ? p->vt[0x68](p, cam, node+0x108, ctx+0xE0) : 0
    ctx+0x270 = OR(p+0x30) | cam+0x8F0
}
// 0x58F7D0(node) — конец узла: vt[0x80] подписанных, обнуляет ctx+0x250/+0x258/+0x260 и ctx+0x150/+0x158
```

Зонд уже перехватывает рисование узла `0x58F0F0` и делает снимок **после** оригинала. В этот момент `ctx+0x250`
ещё указывает на камеру узла: на этом держится `MaskByCamera` с `.15`. Значит, рисование идёт между подготовкой и концом
узла, и ответы `+0x30` в нём — ответы для этого узла.

Ограничения:
- перехват рисования — горячий путь, 600–720 узлов в секунду. Без блокировок, выделения памяти и лога, чтение только
  под SEH (как `capture`);
- отладочные слоты: 0 — зонд плоской камеры, 1 — `native_vr_probe`, 2 и 3 — этот зонд;
- правка меток `.18` каждый кадр пишет позу камер PostGUI (`cam+0x20`) и стоит всегда при `native_vr_on_foot` на ногах.

## Goals / Non-Goals

**Goals:**
- одна прогулка различает исходы P1–P5 (решение 6);
- ошибку самого зонда (не тот момент, не та память) видно в логе, и её не спутать с ответом игры.

**Non-Goals:**
- новые перехваты и сверка байтов новых функций;
- поиск точек зонда по узору (зонд временный, он стоит на билде 334473, как и раньше);
- разбор, что именно рисует поставщик: это статика после прогулки.

## Decisions

### 1. Перепись в уже стоящем перехвате рисования узла, после оригинала

Снимок поставщиков делается там же, где снимок узла, и только для узла листов 36–39.
- *Почему:* нового перехвата и новой сверки байтов не нужно. Момент тот же, на котором `.15`/`.16` уже читали верную
  маску.
- *Альтернатива:* перехватить саму подготовку `0x58F940` и читать после неё. Это точнее по времени, но это новая точка
  со своими 16 байтами и ещё один горячий перехват (вызывается для всех узлов сцены). Отложено: понадобится, только если
  сверка (решение 2) покажет, что снимки не сходятся.

### 2. Сверка снимка: два условия

Снимок верен, только если `ctx+0x150 == node` (подготовлен этот узел, конец ещё не прошёл) и
`OR(p+0x30) | cam+0x8F0 == ctx+0x270`. `ctx+0x250` для сверки не берётся: если подготовка не пересчитывала маску (ветка
`node+0xD8 != 0`), он может остаться от прошлого кадра. Неверные снимки считаются по причине: «контекст другого узла»
или «OR не равен маске». Первая несошедшаяся пара значений один раз за запуск выходит в лог. Так «все снимки не сошлись»
на прогулке сразу говорит, что нужна точка из альтернативы решения 1.

### 3. Где копится: таблица на стороне перехвата, перепись — через маленькое кольцо

- Перехват на каждом верном снимке обновляет атомарную таблицу поставщиков (64 строки, ключ — адрес поставщика и вид).
  В строке: таблица методов, `vt+0x68`, последняя подписка, последний ответ и по трём местам — кадры, кадры с
  подпиской, кадры с `0x8`. Место перехват берёт из уже публикуемого кадровым потоком `g_place`. Лишние поставщики
  идут одним числом.
- «Форма» состава — хэш из числа поставщиков, их адресов, таблиц методов и признака «подписан на камеру узла». Перехват
  хранит последнюю форму по виду. При смене формы (или места) он кладёт полную перепись в кольцо на 4 записи; переполнение
  только считается.
- Кадровый поток пишет перепись из кольца (не чаще раза в 5 с на вид, держит последнюю отложенную) и раз в 30 с —
  сводку по таблице.
- *Почему не писать перепись каждый кадр в кольцо:* около 2 КБ на снимок при ~70 снимках в секунду — лишняя нагрузка
  ради данных, которые и так копятся в таблице.

### 4. Таблица методов и метод ответа — как смещения в exe

В строке переписи — `vtable` и `*(vtable+0x68)` как `+0x…` от базы игры, если они внутри образа. Иначе — абсолютный
адрес с пометкой. По `vt+0x68` статика после прогулки сразу открывает нужную функцию в Ghidra. По одной таблице методов
это не всегда видно: таблицы могут наследоваться, а у поставщиков одного класса метод общий.

### 5. Сторож: слот 2 — подписка поставщика `_HUD`, слот 3 свободен

Сторожа `.16` (камера и маска) снимаются из кода зонда. Слот 2 берёт подписку `p+0x28` (младшие 4 байта: в них биты
обеих камер PostGUI, `0x4` и `0x800000`) первого поставщика, у которого в сошедшемся снимке был бит `0x8`.
- Цель ставит кадровый поток при первом таком поставщике. Если поставщик пропал из переписи своего вида на 2 с, сторож
  снимается со строкой: на освобождённой памяти он ловил бы чужие записи.
- Обработчик пишет место записи, значение (8 байт) и «есть ли в нём бит камеры узла HUD». Биты камер узлов HUD обоих
  видов кадровый поток публикует атомарно.
- Обработчик, таблица мест, предохранитель 100 000 за 30 с, строки «watch on/off/moves» — существующая механика
  `.16`. Меняются цель, имя (`hud provider subscription`) и счётчик «с битом камеры» вместо «с битом `_HUD`».
- *Почему не оставить сторож камеры:* он ловил бы каждый кадр записи правки меток. Его ответ (`+0x59F313`) уже есть.
  *Почему не сторож маски на слоте 3:* её пишет только `0x58F940`, это уже известно.
- *Почему сторож на подписку, а не на ответ `p+0x30`:* ответ переписывается каждой подготовкой каждого узла. Сторож дал
  бы сотни срабатываний в секунду и ничего нового сверх таблицы ответов.

### 6. Какие исходы различает прогулка

| Исход | Признак в логе | Дальше |
|---|---|---|
| P1 — в стерео поставщик не подписан на камеру узла HUD | в кинотеатре у X «подписан» и `0x8`; в стерео X в списке, «не подписан» | строка сторожа: кто переписал `+0x28` при выходе в стерео |
| P2 — подписан, но отвечает без `0x8` | в стерео X «подписан», кадры с подпиской есть, с `0x8` — 0 | статика `X.vt+0x68`: что в нём смотрит на режим |
| P3 — поставщика нет в списке в стерео | в стерео X нет в переписи | кто добавляет поставщиков в сцену (`vt+0x20`, `0x6BDE40`) |
| P4 — бит даёт сама камера | в кинотеатре `0x8` есть в `cam+0x8F0`, ни один поставщик его не даёт | кто пишет `cam+0x8F0` (`0x2820A00`) |
| P5 — снимок не тот | «не сошлось» — заметная доля | точка из альтернативы решения 1, ещё один круг |

### 7. Статика после прогулки — инструменты прошлых сессий

`g.ps1` и `gs\DecompRva.java` копируются в scratchpad этой сессии из `2a965640…\scratchpad\re\`. Проект Ghidra
`C:\tools\ghidra_projects\ED334473` открывается только для чтения, игру при этом не запускать. Разбирается `vt+0x68`
поставщика из исходов P1/P2 и его вызовы на 1–2 уровня.

## Risks / Trade-offs

- [Поставщиков десятки, перепись длинная] → строка на поставщика только в переписи; перепись пишется при смене формы и не
  чаще раза в 5 с на вид. В сводке — только подписанные хоть раз или ответившие непусто.
- [Ответы `+0x30` — маски внутри набора листов узла, а не общие номера листов] → бит `0x8` проверяется только у узла
  листов 36–39 (первый лист 0, четыре листа), как маска `pose` с `.15`.
- [Поставщик освобождён, а сторож стоит] → снятие по пропаже из переписи на 2 с, плюс предохранитель.
- [В кинотеатре вид 1 узла HUD не рисует] → поставщика `_HUD` ищем по виду 0. Вид 1 виден в переписи стерео.
- [Зонд и правка меток пишут/читают одно и то же] → зонд камеру PostGUI только читает (позы `.15`). Сторожа на ней больше
  нет.
- [Зонд должен остаться незаметным] → весь новый код — чтение и счёт. Горячий путь — один проход по списку на узел HUD
  (~70 раз в секунду), остальные узлы отсекаются, как и раньше, по виду узла.

  одну прогулку, после разбора — обратно 0.
- Откат — переустановка `.18` (`install_edvr.py` с тегом прошлой сборки). Правка меток и остальной EDVR не меняются.
