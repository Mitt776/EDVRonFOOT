# Design

## Context

Мотив — в proposal.md (Why). Что известно на сейчас: исследование, разделы «Прогулка `.19`» и «Статика: поставщик
`_HUD`». Декомпиляция `0x4C82940`, `0x4C7E630`, `0x4C84360`, `0x4C85280`, `0x4C812E0`, `0x4C80480` лежит в
scratchpad прошлой сессии (`30c14356…\scratchpad\re\range.c`, `b2.c`–`b4.c`). `0x4C7C620` — в scratchpad этой сессии
(`8e8548a1…\scratchpad\re\c1.c`).

Как устроен ответ B (билд 334473, всё — смещения полей):

```

rec  (0x108 байт, конструктор 0x4C812E0):  +0x08 B,  +0x10 bnd,  +0x100 ответ (u64),  +0xE8 контейнер групп

сетка m:    +0x00 ресурс R,  +0x10 данные экземпляров,  +0x18 маски экземпляров (u64 на экземпляр),

материал:   mat = *(M + 0x10 + номер*8);   проход p = *(mat + 0xB8 + view*8);   байт p+0x60 — «включён»
```

Ворота по пути (сетка, секция, материал), в порядке `0x4C82940`/`0x4C7E630`:

| № | Ворота | Открыты, если |
|---|---|---|
| G1 | группа | `g + slot*4` ≠ 0 |
| G2 | элемент | `it + 0x38 + slot*4` ≠ 0 |
| G3 | часть | `s + 0xD8 + slot*4` ≠ 0 |
| G4 | маска сетки | `m+0x30 & bnd+0x28` ≠ 0 |
| G5 | экземпляры | есть экземпляр этой секции с `маска_i & bnd+0x28` ≠ 0 |
| G6 | проход вида | `mat + 0xB8 + view*8` ≠ 0 |
| G7 | проход включён | байт `p+0x60` ≠ 0 |

Ограничения — те же, что у `.19`: перехват рисования узла — горячий путь, чтение только через SEH-читатель, без
блокировок, выделения памяти и лога. Отладочные слоты: 0 — зонд плоской камеры, 1 — `native_vr_probe`, 2 — этот зонд,
3 свободен.

## Goals / Non-Goals

**Goals:**
- одна прогулка называет первые закрытые ворота путей `_HUD` в стерео (исходы Q1–Q7, решение 7);
- если ворота закрываются записью, та же прогулка даёт её место (сторож ворот и второй выход в стерео);
- ошибку самого зонда видно в логе: сверка ответа записи и пересчёта.

**Non-Goals:**
- разбор семи сборщиков из таблицы `0x6054C70`: зонд только называет их адреса и говорит, если бит пришёл от них;
- новые перехваты, поиск точек по узору (зонд временный и стоит на билде 334473);
- чтение диапазонов `rec+0x60..0x88`: ворота G5 зонд считает прямо по экземплярам, как `0x4C80480`.

## Decisions

### 1. Обход — в том же перехвате рисования узла, раз в секунду на вид

Обход делает `providersOfHudNode` после сошедшегося снимка, если в нём есть поставщик с таблицей `base+0x5A72D58`.
Частоту держит атомарная метка времени на вид (CAS): не чаще раза в 1000 мс.
- *Почему здесь:* в этот момент `p+0x30` у B — ответ этого кадра для этой камеры. С ним сверяется `rec+0x100`
  (решение 4). Новых точек и сверки байтов не нужно.
- *Почему раз в секунду:* обход — сотни и тысячи чтений. Каждый кадр (~70 узлов HUD в секунду) — лишняя нагрузка на
  поток рисования. Ворота — данные, они меняются при смене места, а не каждый кадр.
- *Альтернатива:* обходить из кадрового потока. Отклонено: там нет ответа этого кадра для сверки, а камеру и набор
  листов узла пришлось бы передавать отдельно.

### 2. Обход идёт по всем секциям, а не по диапазонам записи

Зонд проходит все группы, элементы, части и сетки контейнера записи, у каждой сетки — все секции ресурса и их
проходы. Ворота G1–G7 читаются для каждого пути, даже если раньше по пути что-то закрыто. Так видно не только первые
закрытые ворота, но и значения остальных.
- *Почему не по `rec+0x70`/`+0x88`:* номер диапазона там — счётчик, общий с семью сборщиками. Без их разбора его не
  сопоставить с сеткой. И диапазоны есть только у открытых путей: закрытый путь из них просто выпадает.
- Бюджет: не больше 16 384 записей проходов и 16 384 экземпляров за обход. Дальше обход обрывается с пометкой
  «не весь». Слот > 63 или вид > 15 — привязке не верим, обход не идёт, причина считается.

### 3. Путь `_HUD` и память о материалах

Путь `_HUD` — тройка (сетка, секция, материал), у которой проход материала дал бит `0x8`. Зонд хранит атомарный набор
до 64 материалов (CAS) с номером вида, при котором проход дал `0x8`. Его пополняет обход при открытом G6 с `0x8` в
битах, в любом месте. Путь входит в запись обхода, если его материал в наборе. У такого пути зонд пишет и проход для
текущего вида, и проход для запомненного вида. Так при закрытом G6 видно, что у материала есть проход `_HUD` для вида
кинотеатра, а для вида стерео нет.
- *Почему материал, а не сетка:* сетки HUD в стерео могут быть другими объектами (новый конвейер при смене места), а
  материалы — общие ресурсы. Адреса сетки, части, элемента и группы всё равно пишутся в строке пути: по ним видно, тот
  же ли это путь.
- В записи обхода до 64 путей `_HUD`, лишние только считаются. Счёт по воротам идёт по всем.

### 4. Сверка: ответ записи и пересчёт

Обход сошёлся, если `rec+0x100 == B+0x30` этого кадра, а OR битов по открытым путям (всем, не только `_HUD`) — часть
`rec+0x100`. Остаток `rec+0x100 & ~пересчёт` — биты семи сборщиков, он пишется в заголовке. Если пересчёт дал бит,
которого нет в `rec+0x100`, обход «не сошёлся»: зонд читает не то. Несошедшиеся только считаются по причине, первая пара
значений — одной строкой. Адреса семи сборщиков (таблица `0x6054C70`, она заполняется при запуске) — одна строка за
запуск, при первом обходе. В обходе считается, у скольких частей непусты списки каждого сборщика.

### 5. Где копится: кольцо на 2 обхода, перепись и сводка — в кадровом потоке

- Перехват кладёт запись обхода (заголовок, счёт по воротам, до 64 путей) в кольцо на 2 записи, переполнение только
  считается. Запись — около 5 КБ, раз в секунду на вид, это немного.
- Кадровый поток ведёт «картину ворот» по виду: хэш из слота, вида, маски привязки, итога сверки и первых закрытых
  ворот каждого пути. При смене картины или места он пишет перепись: заголовок и до 16 путей. Пишет не чаще раза в 5 с
  на вид, последнюю отложенную держит.
- Раз в 30 с — сводка по местам: обходы, сошедшиеся, несошедшиеся по причине, нечитаемые и счёт путей `_HUD` по первым
  закрытым воротам у последнего сошедшегося обхода каждого вида.
- Кадровый поток помнит по каждому пути `_HUD` последнее состояние в кинотеатре. Оно нужно для выбора цели сторожа.

### 6. Сторож ворот на слоте 2

Сторож подписки `.19` и выбор его цели убираются. Цель сторожа ворот ставит кадровый поток при первом пути `_HUD`,
который в кинотеатре был открыт, а в сошедшемся обходе в стерео закрыт. Сторожится слово первых закрытых ворот:

| Ворота | Адрес | Длина |
|---|---|---|
| G1–G3 | флаг слота стерео-привязки | 4 |
| G4 | `m+0x30`, если её значение изменилось против кинотеатра, иначе `bnd+0x28` стерео | 8 |
| G5 | маска первого экземпляра этой секции | 8 |
| G6 | `mat + 0xB8 + view*8` вида стерео | 8 |
| G7 | байт `p+0x60` | 1 |

Адрес не выровнен под длину — берётся длина 4 или 1 с выровненным адресом внутри слова. Обработчик пишет место,
значение и «открывает ли ворота»: для флага, прохода и байта — не 0. Для маски — пересекается ли значение со второй
маской, её кадровый поток публикует атомарно. Если путь пропал из обходов своего вида на 2 с, пока узел рисуется,
сторож снимается со строкой. Таблица мест, предохранитель 100 000 за 30 с, строки «watch on/off/moves» — механика `.16`
и `.19`. Меняются цель, имя (`hud gate <ворота>`), длина и признак «открывает».
- *Почему второй выход в стерео:* ворота закрываются, скорее всего, при выходе в стерео. Сторож встаёт только после
  первого обхода в стерео, это уже после записи. Возврат в корабль и второй выход в стерео дадут запись при стороже.
- *Почему G6 тоже сторожится, хотя пустой слот вида может никто не писать:* молчание сторожа там — тоже ответ
  («проход для вида стерео никто не ставит»). Искать его тогда — в статике.

### 7. Какие исходы различает прогулка

| Исход | Признак в логе | Дальше |
|---|---|---|
| Q1 — пути закрыты флагом слота (G1–G3) | в стерео первые закрытые ворота группа/элемент/часть; слот привязки тот же или другой — видно в заголовке | писатель флага: строка сторожа или ссылки на `+0x38`/`+0xD8` в Ghidra |
| Q2 — маски камер не пересекаются (G4) | закрыта маска сетки; видно, какая из двух масок другая | писатель изменившейся маски |
| Q3 — нет экземпляров для камеры (G5) | закрыты экземпляры | писатель масок экземпляров |
| Q4 — у материала нет прохода для вида стерео (G6) | закрыт проход вида; проход для вида кинотеатра есть | кто строит проходы материала по видам (`mat+0xB8`) |
| Q5 — проход выключен (G7) | закрыт байт `p+0x60` | писатель байта |
| Q6 — бит `0x8` не из сеток | в кинотеатре `0x8` в остатке сборщиков, путей `_HUD` нет | статика сборщика из таблицы `0x6054C70` |
| Q7 — обход не тот | «не сошлось» — заметная доля, или записи нет | исправить разбор, ещё круг |

## Risks / Trade-offs

- [Обход тяжёлый для потока рисования] → раз в секунду на вид, бюджет 16 384 + 16 384, обрыв с пометкой.
- [Игра меняет элементы во время обхода] → чтение через SEH-читатель, сверка решения 4 отсеет кривой обход.
- [Структура понята не до конца, и смещение неверно] → сверка пересчёта с `rec+0x100` в кинотеатре сразу это
  покажет (Q7), а не даст ложного ответа.
- [В стерео материалы HUD другие, а не те, что в кинотеатре] → пути `_HUD` в стерео тогда не найдутся. Перепись скажет
  «путей 0», сводка покажет число путей по местам, а адреса сеток и частей в строках кинотеатра дадут сверить руками.
  Это тоже ответ: стерео строит HUD из других объектов.
- [Сторож на освобождённой памяти] → снятие по пропаже пути на 2 с, плюс предохранитель.
- [Зонд должен остаться незаметным] → весь новый код — чтение и счёт, сторож только читает в обработчике.

## Migration Plan

- Сборка `v0.19.1-edvronfoot.20`, установка `install_edvr.py`. В живом `edvr.ini` через Edit `on_foot_hud_probe = 1` на
  одну прогулку, после разбора — обратно 0.
- Откат — переустановка `.19` (`install_edvr.py` с тегом прошлой сборки). Правка меток и остальной EDVR не меняются.

## Open Questions

- Сколько элементов у B на деле и укладывается ли обход в бюджет — покажет первая же перепись (пометка «не весь»). Если
  не укладывается, бюджет поднимается правкой константы. Подход от этого не меняется.
