# Design

## Context

Зачем это нужно, см. proposal.md. Что известно из статики (билд 334473, исследование «После `.14`»):

- **Переключатель прохода `0x28AD4A0(pass, bool)`.** Его зовёт кадровая `0x2889A00`: для вида 0 — всегда, для
  вида 1 — когда у прохода `+0x328` ≠ 0. Начало функции:

  ```
  40 53 48 83 EC 20 48 8B 99 E0 02 00 00 38 53 70
  push rbx; sub rsp,0x20; mov rbx,[rcx+0x2E0]; cmp [rbx+0x70],dl
  ```

  Это 13 байт простых команд без ссылок по `rip`, так что перехват `CodeHook` подходит.
- **Поля прохода** (`0x28A7370`): `+8` — номер вида (int); `+0x48` — основная камера вида; `+0x50` — камера PostGUI.
- **Камера** (объект `0x900` байт):
  - блок позы с `+0x20`: три строки поворота по 4 float — `+0x20`, `+0x30`, `+0x40`; положение — `+0x50`
    (`0x4F2C20` вычитает его из нового положения, `0x28A7370` обнуляет `+0x50/+0x58`);
  - `0x5A8CD0` копирует блок в `+0x310` («поза кадра»);
  - флажки `+0x18` и `+0x250` — те же, что зонд `.13` уже пишет.
- Голова — `edvr::headPose(float* m12)`, строки 3x4, публикуется каждый кадр (`src/common/frame_flag.h`).
- Зонд `.13` уже держит узлы HUD по видам и их снимок с маской кадра `ctx+0x270` и камерой `ctx+0x250`.

## Goals / Non-Goals

**Goals:**
- Одной прогулкой (кинотеатр, потом стерео) различить M1/M2/M3 по строкам лога.
- Никакой записи в память игры. Пятый перехват только запоминает проход.

**Non-Goals:**
- Исправлять камеру PostGUI (следующая заявка, если подтвердится M2).
- Искать покадровое обновление камеры статикой.

## Decisions

1. **Проход берём из перехвата `0x28AD4A0`, а не ищем через объекты.** Перехват на игровом потоке до оригинала
   кладёт указатель `pass` в таблицу на 4 ячейки: захват свободной ячейки через «сравнить и обменять», дубликат не
   кладётся. Больше он ничего не читает. Вызов оригинала — с теми же аргументами.
   Кадровый поток освобождает ячейку прохода, который игра не зовёт 2 с: посадка и высадка пересобирают конвейер, и
   без этого таблица забилась бы старыми проходами. Новый проход в ячейке — одна строка (вид, обе камеры).
   *Альтернатива:* цепочка `X+0x1180 → +0x2CB8 → +0x90/+0x98` требует `X`, параметр той же кадровой функции, —
   опять перехват, только сложнее.
2. **Читает поток кадра, под SEH.** Раз в 0,5 с (на ногах по журналу) или 5 с (в корабле) для каждого `pass` из
   таблицы зонд читает:
   - номер вида `pass+8`;
   - обе камеры (`+0x48`, `+0x50`) — блок `+0x20..+0x5F` (12 float поворота и положение);
   - флажки `+0x250` камеры PostGUI.

   Возможна порванная запись (игра пишет в тот же момент), для зонда это допустимо. Сводка устойчива к одиночным
   выбросам: выборка, где курс скачет больше чем на 90° за 0,5 с, в коэффициент не идёт и считается отдельно.
3. **Углы.** «Вперёд» — третья строка поворота (`+0x40`), «вверх» — вторая (`+0x30`):
   - курс = `atan2(f.x, f.z)`;
   - тангаж = `asin(f.y)`;
   - крен = `atan2(r0.y, r1.y)`.

   Голова (OpenVR, −Z вперёд, строки 3x4): курс = `atan2(−m[2], −m[10])`, тангаж = `asin(−m[6])`. Соглашение осей
   игры не известно, поэтому в строке есть и сырые 9 чисел поворота камеры PostGUI (3 знака) — разбор можно
   переделать по логу. Главный вывод не зависит от соглашения: обе камеры игры в одном соглашении.
4. **Коэффициент следования.** Между соседними выборками одного вида: `dPost`, `dMain`, `dHead` — приращения курса,
   приведённые к (−180°, 180°]. Коэффициент `k = Σ(dPost·dMain) / Σ(dMain²)` (наклон прямой через 0). То же для
   основной камеры против головы: `Σ(dMain·dHead) / Σ(dHead²)`. «Мало данных» — для первого, если `Σ|dMain| < 20°`,
   для второго, если `Σ|dHead| < 20°`: в кинотеатре голова не поворачивает камеру игры, и «основная против головы»
   около 0 — это ответ, а не нехватка данных. Шаг берётся только между выборками не дальше 1,5 с и в одном режиме
   (выборки в корабле раз в 5 с шагов не дают). Сводка — раз в 30 с, отдельно по виду и режиму, потом сброс. Рядом —
   строка переключателя: вызовы за 30 с (0 — перехват не сработал), проходы в таблице, новые и освобождённые.
5. **Режим** — по ключу `native_vr_on_foot`, прочитанному в этом кадре: 1 — стерео, 0 — кинотеатр.
6. **Маска кадра для вида** — из снимка зонда `.13`: берём узел HUD, у которого камера `ctx+0x250` = `pass+0x50`.
   Если такого нет — «?». Так номер вида и бит вида (8/49) не надо сопоставлять наугад.
7. **Объём лога:** 2 вида × 2 строки/с × ~2 мин на ногах — около 500 строк; в корабле — 2 строки за 5 с.
   Строки короткие: углы с одним знаком, сырые числа только у камеры PostGUI.

## Risks / Trade-offs

- [Строки поворота на деле столбцы] → курс считается не тот. Коэффициент PostGUI против основной всё равно верен (оба
  неверны одинаково), а по сырым числам вывод можно пересчитать.
- [Вид 1 не вызывает переключатель (`+0x328` = 0)] → в таблице один проход; строка вида 1 не появится, это тоже
  ответ (M3).
- [Камера PostGUI обновляется после переключателя в том же кадре] → выборка на потоке кадра у Present видит позу
  после всех записей кадра, ближе к тому, что нарисовано.
- [Перехват на горячем пути] → только поиск в 4 ячейках и запись указателя, без строк и без выделения памяти.

## Migration Plan

Ключ тот же, `on_foot_hud_probe` (0 по умолчанию). Перед прогулкой — 1 в живом `edvr.ini`, после — 0. Откат —
установка `.14`.
