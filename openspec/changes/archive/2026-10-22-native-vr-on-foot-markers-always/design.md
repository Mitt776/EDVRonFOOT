# Design

## Context

Правка позы PostGUI (`.17`, архив `2026-10-22-native-vr-on-foot-postgui-pose`) устроена так:
- чистое ядро — `edvr/src/d3d11/on_foot_markers_core.h`;
- перехваты, установка и шаг кадра — `edvr/src/d3d11/on_foot_markers.cpp`;
- стенд — `edvr/tools/on_foot_markers_test/on_foot_markers_test.cpp`: часть A проверяет ядро, часть B — настоящий
  CodeHook на синтетических писателях с байтами игры.

Что сейчас держится на ключе и на сборке:
- **Ключ.** `parseKey` разбирает `stereo` / `flat` / `off`. `decide(native, keyMode, onFoot)` выдаёт режим.
  `correct(in, mode, out)` считает положение глаз по режиму. Строка `formatKey` выводится при смене ключа.
  Сводка и строка «on» называют режим.
- **Сборка.** `onFootMarkersInstall` сначала сверяет метку PE и размер образа с 334473
  (`kExpectedTimestamp` / `kExpectedImageSize`). Потом сверяет 16 байт у трёх точек по жёстким RVA (`kPointRva`) и
  ставит два CodeHook через релейные страницы.
- **Недочёт образца.** `SampleBox::want()` переводит состояние только из `Idle` в `Wanted`. Если правка выключилась,
  пока образец лежал в `Ready`, то при следующем включении `want()` ничего не делает. Первая сводка нового выхода
  на ноги тогда берёт старый образец.

В проекте уже есть поиск по узору: `nvp::findPatternTarget` в `edvr/src/d3d11/native_vr_probe_core.h` и обход секций
образа в `native_vr_probe.cpp`, функция `sehFindSwitch`. Он ищет **цель RIP-относительного чтения**, а нам нужен
**адрес начала функции**. Байт кинотеатра на 334473 ищется 15 мс, переключатель HUD — 47 мс.

Факты по exe 334473, проверены этой заявкой: Python и capstone по файлу, секция `.text` = RVA `0x1000`, размер
`0x4DB4AEE`.

## Goals / Non-Goals

**Goals:**
- Один режим: `stereo`. Ключа нет, правка зависит только от `native_vr_on_foot`, журнала и аварийного выключателя.
- Три точки находятся по узору на любой сборке, где их код не изменился, с перекрёстной сверкой.
- Первая сводка каждого выхода на ноги показывает свежий образец.

**Non-Goals:**
- Подёргивание прицела (36 к/с на ногах были и до правки) — отдельно, если начнёт мешать.
- Зонд `.18` для основного HUD, удаление ключей зондов (`on_foot_hud_probe`, `native_vr_probe`,
  `native_vr_on_foot_game_hud`).
- Общий поисковик для всех узоров проекта. `nvp::findPatternTarget` не трогаем: у него другой результат
  (цель чтения, а не вход функции) и свои тесты.

## Decisions

### D1. Ключ и вариант `flat` уходят целиком

**Как.**
- Из ядра уходят `Mode`, `Key`, `parseKey`, `formatKey`, `kWhyKey`, ветка `flat` в `correct`.
- `decide(native, onFoot)` отдаёт «вкл» или «выкл» с причиной.
- `correct(in, out)` всегда считает `stereo`.
- `g_mode` в `.cpp` становится `std::atomic<bool> g_on`, `onFootMarkersSetMode` — `onFootMarkersSetOn`.
- `onFootMarkersFrameStep` теряет параметр `keyText`.
- `onFootMarkersFrameBoundary` больше не читает `experimental.native_vr_on_foot_markers`.
- Строки:
  - «on» — `on-foot markers: on (on foot)`;
  - сводка — `on-foot markers: 30 s: ...`, без слова режима;
  - строка о том, что без `native_vr_on_foot` правка не работает, остаётся. Её выводит переход `decide` в `off
    (native_vr_on_foot is off)`, как и сейчас.

**Почему не оставить ключ «на всякий случай».** Правило проекта: исправление, которое всегда помогает, выключателя не
получает. Дима выбрал удаление. Аварийный выключатель по сбоям фиксации остаётся.

**Блок в ini.** Блок `native_vr_on_foot_markers` с комментарием и строкой `# ui:` удаляется из `edvr/edvr.ini`. Контракт
настроек (`build/gen/config_contract_gen.h`) генерируется из него, меню F8 строится по строкам `# ui:`. Пункт уходит
сам, а `check_config_contract.py` в сборке подтвердит, что контракт сошёлся.

### D2. Поиск трёх точек: узор входа у каждой и сверка через писателя позы

**Узоры.** Четыре узора из таблицы в Context.
- Маски закрывают только то, что пересборка меняет легко: размер кадра стека, смещения полей, не связанные с камерами,
  смещение к `__security_cookie`, адрес `__chkstk`.
- Без маски остаются:
  - форма пролога. CodeHook переносит первые инструкции, поэтому они должны остаться теми же;
  - смещения, которые правка сама использует: `0x7F0`, `0x1180`, `0x2CB8`, `0x90`, `0x98` в цепочке и `0x230` (флаги
    блока) в фиксации.

**Правило.**
1. Один проход по исполняемым секциям образа. Каждая позиция проверяется на три узора входа. Якорь — первый байт:
   `0x48` или `0x40`, как `memchr` в `findPatternTarget`. Совпадения считаются по каждому узору.
2. Каждый узор входа должен найтись ровно 1 раз. Иначе отказ «точка X: N совпадений».
3. Сверка с писателем позы, который должен:
   - содержать узор цепочки в первых `0x100` байтах;
   - содержать `E8 rel32` на найденный вход писателя глаз в первых `0x400` байтах;
   - содержать `E8 rel32` на найденный вход фиксации в первых `0x400` байтах.

   Не сошлось — отказ с названием сверки. Окна `0x100` и `0x400` — в 3–4 раза шире фактических смещений (`+0x47`,
   `+0x1AE`, `+0x24A`). Этот запас на рост функции, но поиск не уходит в соседние функции.
4. Нашлось — `at[kPoint*] = base + rva`. Дальше всё как сейчас: релеи и два CodeHook.

**Что убираем.**
- Сравнение 16 байт (`kPointPrologue`): узор входа его заменяет и строже по форме.
- Проверка метки PE (`kExpectedTimestamp` / `kExpectedImageSize`): с поиском по узору она только мешает.

**Почему вход каждой функции, а не одна точка и переход по вызовам.**
- Найти фиксацию только по вызову из писателя позы — значит доверять, что первый «какой-то» вызов и есть она.
- Отдельный узор входа плюс сверка вызова ловят оба вида сдвига: функцию заменили, и вызов ведёт в другое место.
- Дима выбрал «уникальная сигнатура у каждой точки».

**Где код.**
- Чистая часть — в `on_foot_markers_core.h`:
  - маскированный узор (`struct Sig { const uint8_t* bytes; const uint8_t* mask; size_t n; }`);
  - `findPoints(image, sections, count) -> Found {result, point, matches, rva[3]}`;
  - строки `formatFound` и `formatNotFound`.

  Стенд гоняет всё это на синтетическом образе. Секции описывает своя маленькая структура `ofm::Section`, так что
  ядро не зависит от `native_vr_probe_core.h`.
- Обход заголовков PE под SEH — в `.cpp`, по образцу `sehFindSwitch`.

**Когда искать.**
- Поиск идёт один раз, на первом кадре, где `native_vr_on_foot` включён, а не при первом выходе на ноги. Проход по
  ~80 МБ может занять десятки мс (два готовых поиска — 15 и 47 мс). На первом кадре это незаметно, а при выходе на
  ноги в шлеме это рывок.
- Перехваты, как и сейчас, ставятся при первом включении правки (первый выход на ноги). В корабле код игры не
  патчится, пока командир не вышел.
- Строка поиска пишется сразу, с временем в мс. Отказ поиска ⇒ решение «off (not installed, the line above says
  why)», как сейчас при несовпадении байт.

### D3. Свежий образец на каждое включение

Когда окно стартует (переход в «вкл»), шаг кадра сначала забирает и выбрасывает лежащий `Ready` образец
(`g_sample.take(&drop)`), потом зовёт `want()`. Для этого в `SampleBox` появляется `reset()`:
- переводит `Ready` → `Idle`;
- `Writing` не трогает: тот образец ляжет в `Ready` и будет выброшен следующим `reset` или взят как образец текущего
  окна. Писатель в это время уже работает на новом включении, так что этот образец свежий.

### D4. Стенд

- **Часть A.**
  - Удаляются проверки ключа и `flat`.
  - `decide` проверяется по двум входам.
  - Добавляется `findPoints` на синтетическом образе: три входа, цепочка и вызовы. Случаи:
    - всё найдено, адреса верные;
    - узора входа нет;
    - узор входа дважды;
    - нет цепочки;
    - нет вызова писателя глаз;
    - нет вызова фиксации;
    - вызов фиксации за окном `0x400`;
    - маскированные байты другие (другой размер стека) — всё равно найдено.
  - Добавляется `SampleBox`: `Ready` → `reset` → `want` → `put` даёт новый образец.
- **Часть B.**
  - Синтетические писатели получают те же байты входа, что у игры, внутри буфера-«образа» с секцией `execute`.
  - Установка идёт через поиск. Отдельного списка `targets` больше нет: в стенд передаётся база синтетического образа
    и его секции.
  - Строки «другая сборка» больше нет. Проверки отказов переносятся на «узор не найден» и «сверка не прошла» —
    ничего не пропатчено, одна строка.
  - Шаг кадра без `keyText`. Выключение и включение (корабль → ноги) даёт свежий образец в первой сводке.
- **Ключ `--exe <путь>`** (ручная проверка, не гейт): стенд читает файл exe, раскладывает секции и печатает результат
  `findPoints`. На 334473 это `0x287D660`, `0x28457F0`, `0x2874820`. В гейт не входит: exe игры нет в репозитории.

## Risks / Trade-offs

- [Патч игры поменяет пролог или размер кадра так, что узор не совпадёт] → Правка не ставится, строка в логе
  называет точку. Это то же, что сейчас при любом патче, только реже.
- [Узор найдёт похожую функцию в новой сборке] → Нужно совпадение ровно одно на каждый из трёх узоров плюс три сверки
  через писателя позы. Ложное совпадение всех шести условий маловероятно. Даже тогда цепочка `locate` проверяет
  каждый кадр номер вида и камеру прохода против `+0x50`. Несовпадение — кадр пропущен и посчитан.
- [Смещения внутри камеры (`0x2E0`, `0x38`, `0x100`, `0x310`, `0x20`, `0x250`) сдвинутся в новой сборке, а узоры
  совпадут] → `locate` проверяет `cam == pass+0x50` и номер вида. Сдвиг даёт пропуски в сводке, а не запись мимо.
  Запись позы и фиксация идут под SEH, три сбоя выключают правку.
- [Поиск на первом кадре дольше ожидаемого] → Время пишется в строку поиска. Если выйдет за ~100 мс, следующая заявка
  перенесёт его в фоновый поток. В этой не переносим, чтобы не усложнять.
- [Пользователь хотел выключить только правку меток] → Такой возможности больше нет, только вместе с
  `native_vr_on_foot`. Это осознанный выбор Димы.

## Migration Plan

- Живой `edvr.ini` в папке игры не меняется. Строки ключа там нет, а если у кого-то есть, она игнорируется.
- Откат: поставить прошлую сборку `v0.19.1-edvronfoot.17` через `install_edvr.py`. Ключ там по умолчанию `stereo`.
