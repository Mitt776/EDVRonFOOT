# Design

## Context

`desktop-eye-mirror` (слит 21.11, `main` cc3a58e) рисует итоговый кадр выбранного глаза в окно игры перед Present.
Рантайм в `finishCapturedEye` (`native_runtime_host.h`) отдаёт кадр через таблицу `edvrAcquireNativeDesktopView`
(версия 1: `noteEye(seq, eye, texture, box)`, `noteMask`, `close`). `d3d11.dll` хранит последний кадр и рисует его
одним треугольником на весь вид. Шейдер переводит пиксель окна в точку кадра линейно: `uv = lerp(src.xy, src.zw, c)`.

Рядом с кадром у рантайма уже лежит то, что нужно для поворота. `frameContentViews[eye]` — это `XrView` с позой и
углами обзора, которыми описаны пиксели этого кадра (с учётом обрезки поля и сдвига при отказе temporal). Поза взята из
`xrLocateViews` на тот кадр, который игра рисовала, в пространстве шлема (без поворота стиком и без корабля).

Облёт 2 (`edvr_gfx_20261121_221917`): глаз 2448×2672, окно 1920×1080, `zoom x1.089`, маска 29 треугольников, цена
0,012–0,024 мс.

## Goals / Non-Goals

**Goals:**
- Убрать из окна мелкое медленное покачивание головы. Быстрые повороты пропускать почти без задержки.
- Не показывать чёрных краёв и углов маски.
- Не менять ничего в шлеме. Цена на видеокарте должна остаться на уровне сотых долей миллисекунды.

**Non-Goals:**
- Не выравниваем горизонт и не убираем крен как таковой.
- Не сглаживаем сдвиг головы без поворота: для этого нужна новая отрисовка сцены, а на экране он почти не виден.
- Не сглаживаем повороты стиком и корабля: они в позу шлема не входят и так плавные.
- Не делаем стабилизацию при `whole`.

## Decisions

### 1. Поворот готового кадра, а не вторая камера

Для каждого пикселя окна берётся луч из сглаженной ориентации `S`. Он поворачивается в ориентацию кадра `P` и
проецируется по углам обзора кадра в его `uv`. Это одна выборка на пиксель, как сейчас.

```
 пиксель окна --> тангенсы (tx, ty) в камере S --> луч (tx, ty, -1)
              --> M = P^-1 * S (матрица 3x3) --> луч'
              --> tx' = x'/-z', ty' = y'/-z' --> uv по углам обзора кадра --> выборка
```

При `S = P` матрица единичная, а тангенсы линейны по пикселям. Поэтому `off` и `on` в покое дают ровно ту же
картинку, что сейчас. Мелкая неточность углов обзора даёт лишь чуть неточную величину поворота, но не сдвиг и не
поломку.

Отвергнуто: вторая камера или перерисовка. Игра рисует сцену сама, третьей камеры нет, и она стоила бы кадров.

### 2. Фильтр «1€» по ориентации, плюс предел отставания

Фильтр работает на стороне `d3d11.dll`, один раз на каждый новый кадр выбранного глаза (по `sequence`). Время берётся
по QPC в момент рисования.

- Скорость поворота считается по углу между соседними позами кадра, сглаженному с частотой среза `dcutoff = 1 Гц`.
- Частота среза: `fc = minCutoff + beta * |скорость|`. При медленном движении она низкая, и фильтр сглаживает
  сильно. При быстром повороте она высокая, и задержки почти нет.
- `S = slerp(S, P, alpha)`, где `alpha = 1 / (1 + tau/dt)` и `tau = 1 / (2*pi*fc)`.
- **Предел отставания** `L = 2°`. Если угол между `S` и `P` больше `L`, `S` подтягивается к `P` до ровно `L`.
  Предел же гасит любые скачки: рецентр, смену начала координат, первый кадр. Первый кадр ставит `S = P`.
  Перерыв больше 0,25 с (загрузка, нет глаза) тоже сбрасывает `S = P`.
- Начальные значения (константы, не ключи): `minCutoff = 0.8 Гц`, `beta = 0.6 1/рад`, `dcutoff = 1 Гц`.
  Подбираются по ролику облёта. Наружу не выносятся: игроку нужен только `on/off`.

Отвергнуто: простое экспоненциальное сглаживание. Оно тянет за собой и резкие повороты, а этого Дима не хочет.
Отвергнуто: мёртвая зона. Она даёт рывок на выходе из зоны, а правила проекта таких порогов избегают.

### 3. Запас кадра: окно меньше на предел отставания

Чтобы поворот до `L` не выводил окно за край кадра или на маску, прямоугольник `crop`/`zoom` считается для «окна,
расширенного на запас». В тангенсах поворот на малый угол `L` сдвигает точку не больше чем на `tan(L)*(1 + t^2)`, где
`t` — наибольший тангенс угла края окна. Поэтому:

- `crop` при `on`: прямоугольник уменьшается так, чтобы с каждой стороны до края кадра оставался этот запас.
- `zoom` при `on`: проверка маски (`zoomShare`) идёт по прямоугольнику, расширенному на тот же запас. Значит, ни
  треугольник маски, ни край кадра в окно не попадут при любом отставании до `L`.

Оценка: при `L = 2°` запас около 4–5 % ширины на сторону, то есть `zoom` вырастет примерно с x1.09 до x1.15–1.2.
Точное число попадёт в лог. Расчёт кэшируется, как сейчас кэшируется `zoom`.

### 4. Таблица версии 2: поза и углы кадра вместе с глазом

`EDVR_NATIVE_DESKTOP_VIEW_VERSION_2`: `noteEye` дополнительно получает ориентацию головы этого кадра (кватернион
`x, y, z, w`) и его углы обзора (`left, right, up, down` в радианах) из `frameContentViews[eye]`. Остальное без
изменений. Рантайм просит только версию 2, `d3d11.dll` отдаёт только её. Обе DLL ставятся одним установщиком. Если
их версии не совпали, таблица не выдаётся, вид из глаза выключен, и это видно в трассе
`native_desktop_view,unavailable=`.

Если поза кадра недействительна, `noteEye` получает признак «нет позы». Тогда этот кадр рисуется без поворота, а
фильтр сбрасывается.

### 5. Шейдер

Константы расширяются: матрица `M` (3×float4), тангенсы окна (`tx0, ty0, tx1, ty1`), углы кадра (тангенсы
`left/right/up/down`) и `bounds` кадра. При `off`, при `whole` и без позы `M` единичная, и шейдер даёт то же, что
сейчас. Шейдеры собираются заранее через `tools\temporal_shader_build`, как сейчас; число шейдеров не меняется, меняется
только код двух шейдеров вида из глаза.

### 6. Ключ и лог

- `native_vr_desktop_view_steady = off | on` в `[experimental]`, по умолчанию `on`; пустой и неизвестный = `on`
  (и в логе отмечается как неизвестный). Строка `# ui: Desktop eye steady | choices on, off | live | menu on_foot` —
  девятая на странице On foot, генератор сам даёт строку в F8 и в установщике.
- В строку лога раз в 30 с добавляется: `steady on, lag mean %.2f max %.2f deg, clamped N` или `steady off`.
  Без новой работы такого хвоста не будет, поэтому по логу сразу видно, что стабилизация вообще работала.

## Risks / Trade-offs

- [Чуть меньше видно по краям] → Запас всего несколько процентов, точное увеличение пишется в лог.
- [Меню F8 и всё, что пришито к голове, в окне слегка «плавает»] → Сдвиг не больше `L = 2°`, на записи это обычно не
  мешает.
- [Параметры фильтра подобраны неудачно: остаётся тряска или ощущается задержка] → Константы меняются в одном месте.
  Решение принимается по ролику (ffmpeg, кадры глазами) и по логу отставания, без новых ключей.
- [Углы кадра не совпадают с его `bounds` при обрезке поля] → На покой это не влияет (единичная матрица). Проверить
  при реализации, какие углы описывают именно область `bounds`, и стендом зафиксировать покой = текущая картинка.
