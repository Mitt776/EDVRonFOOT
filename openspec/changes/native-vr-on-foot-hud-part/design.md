# Design

## Context

Мотив — в proposal.md (Why). Что известно на сейчас: исследование, разделы «Зонд `.20`» (карта полей записи B) и
«Прогулка `.20`» (адреса HUD-части кинотеатра, слепое пятно). Карта полей — в design архива
`2026-10-23-native-vr-on-foot-hud-gates`. Из неё нужно здесь:

```
часть s:   флаг s+0xD8+slot*4;  сетки: +0x08 число (u64), +0x10 массив (шаг 0x48)
сетка m:   +0 ресурс R, +0x28 набор материалов M, +0x30 маска камер, +0x3C число экземпляров
ресурс R:  +0x38 число секций, +0x40 секции (шаг 0x10: начало, конец — диапазон записей проходов), +0x80 записи (номер)
материал:  mat = *(M+0x10+номер*8);  проход вида v: p = *(mat+0xB8+v*8);  байт p+0x60 «включён»;  листы *(*(p+0x50)+0x30)
```

Рисование узла (`0x58F0F0`, декомпиляция — scratchpad сессии `3c9a55d7…\scratchpad\re\d14.c`, `d15.c`; билд 334473):

```
ctx = *(S+0x60), S = *(node+0x108);  для i в диапазоне листов узла (node+0xD8, число node+0xE0):
    L = *(*(S+0x70) + i*8)
    0x592090(ctx, L, 0)      -- если L+0x30 & ctx+0x270: готовит константы листа (отображение буфера), камеру
    0x594EF0(ctx, L)
    если L+0x30 & ctx+0x270:  (ctx+0x188)->vt[0x38](L)      -- само рисование листа
```

`L+0x30` — бит листа в наборе PostGUI: `1 << i`, i = 0..3 — листы 36–39. `0x592090` отображает буфер констант на
вызывающем потоке. Это признак того, что рисования листа идут здесь же, но не доказательство.

Путь рисований EDVR: `beginPanelOverride` (`vscreen.cpp`) получает каждое рисование четырёх видов (`Draw`,
`DrawIndexed`, `DrawInstanced`, `DrawIndexedInstanced`). Ветка чужого контекста (`foreignContext`) стоит раньше
`drawGateWanted`. Тень привязок (`binding_shadow.h`) знает только свой контекст: `Rtv0`, `PsSrv0..3`, хэши `Vs`/`Ps`.
Чужой контекст перепись рисований читает геттерами контекста (`drawCensusDrawDirect`). Шейдеры сеток HUD в
кинотеатре (`.9`): `vh=B10B032BDFD46700` (ps `DB899F4BD577F2E5`) и `vh=C4B4B334B26E81A9` (ps `0146ABCC53240479`).

Ограничения — те же, что у `.20`: перехваты — горячий путь, чтение только через SEH-читатель, без блокировок,
выделения памяти и лога. Отладочные слоты: 0 — зонд плоской камеры, 1 — `native_vr_probe`, 2 — этот зонд (сейчас
сторож ворот), 3 свободен.

## Goals / Non-Goals

**Goals:**
- одна прогулка называет исход для HUD-части в стерео (R1–R5, решение 8) и для текстуры листа `_HUD` (T1–T3);
- если часть наполняется записью, та же прогулка даёт место писателя (сторожа части);
- «зонд ничего не увидел» отличимо от «игра ничего не делает»: у каждого нового счёта есть строка «0».

**Non-Goals:**
- связь «рисование ↔ сетка» по диапазону индексов: секции ресурса — диапазоны записей проходов, а не индексов.
  Рисования листа 39 сопоставляются с путями `_HUD` по числу и порядку;
- чтение формы рисований на чужом контексте вне узла (цена — геттеры на каждое такое рисование);
- разбор семи сборщиков `0x6054C70` (в `.20` остатка нет).

## Decisions

### 1. HUD-часть узнаёт кадровый поток по обходу кинотеатра, читает её обход

Кадровый поток уже держит последний сошедшийся обход каждого вида. В кинотеатре он берёт часть с наибольшим числом
открытых путей `_HUD`. Её группа, элемент и часть (адреса и номера в массивах) публикуются для перехвата атомарно,
с номером поколения. При смене части в кинотеатре — новое поколение и строка «HUD-часть сменилась».
- Обход `.20` проходит все части. Встретив запомненную часть, он читает её целиком (решение 2). По пути он отмечает,
  что стоит на запомненных местах (группа i, элемент j, часть k). Так строка «части нет в записи» называет замену.
- По старому адресу вне записи зонд не читает: там может быть освобождённая память и случайные значения.
- *Альтернатива:* искать часть заново в стерео по признаку (число сеток, материалы). Отклонено: именно это и
  неизвестно, признак «как в кинотеатре» дал бы пустой ответ.

### 2. Чтение HUD-части: все сетки, все записи проходов, все виды

Для части: флаг слота привязки, маска слотов с ненулевым флагом (0–63), счёты списков семи сборщиков, число сеток,
адрес массива. Для каждой сетки (до 16): ресурс, число секций, экземпляры (сколько и OR масок), маска камер. Для
каждой записи прохода (до 8 на сетку): номер, адрес материала и по 16 видам — маска видов с проходом, маска видов с
`on=1`, маска видов с листом `_HUD` (`0x8`), листы прохода для вида набора и OR листов по всем видам.
- Итог части: **пуста** (0 сеток или 0 записей) / **нет прохода `_HUD`** (ни у одного материала ни для одного вида) /
  **`_HUD` только для другого вида** (виды названы) / **`_HUD` для вида набора**.
- Запись чтения — около 5 КБ, добавляется к записи обхода в кольце на 2 (как у `.20`). Обход и так раз в секунду на вид.

### 3. Проходы `_HUD` по всем видам — по разным материалам записи

Обход собирает адреса материалов в таблицу на 2048 мест (открытая адресация, на стеке) и не больше 1024 разных
проверяет по 16 видам (16 384 чтения). У каждого элемента — счёт материалов с `0x8` для вида набора и с `0x8` только
для других видов. До 8 материалов второго рода называются (элемент, часть, маска видов).
- *Почему по материалам, а не по путям:* материалы общие у многих сеток. По путям чтений было бы в десятки раз больше.
- *Почему всю запись, а не только HUD-часть:* в стерео HUD может строиться в другом элементе. Тогда перепись
  элементов это покажет.

### 4. Окно узла HUD и лист: перехват `0x592090`

- Перехват рисования узла `0x58F0F0` до оригинала читает вид узла (те же 3 поля, что сейчас после). Если это узел
  листов 36–39, он открывает окно: поток, бит вида, номер места. После оригинала окно закрывается.
- Новый перехват `0x592090` (до оригинала): если поток — поток открытого окна, лист = номер младшего бита
  `*(L+0x30)` (0–3), иначе ничего. Стоит на 16 байтах начала с проверкой, как остальные точки.
- *Почему `0x592090`, а не `0x594EF0`:* она первая на каждом листе и сама отображает его константы. Рисования внутри
  неё и после — этого листа.
- *Альтернатива без перехвата:* делить рисования узла по маске кадра. Отклонено: в кинотеатре горят листы 38 и 39
  вместе (`0x20C`), а нужно отличить `_HUD` от `_PanelForeground`.

### 5. Приём рисований: один вызов в `beginPanelOverride`

`onFootHudProbeNoteDraw(ctx, kind, count, instances, args, own)` стоит в `beginPanelOverride` до ветки чужого
контекста, под встроенной проверкой атомарного флага. Флаг поднят, пока ключ включён и перехваты стоят.
- **В окне** (поток окна): форма рисования. Это лист, вид, место, свой или чужой контекст, вид и число рисования,
  хэши VS и PS, цель 0 (токен, ширина, высота, формат) и текстуры PS 0–7: токен, ширина, высота, формат, «цель
  рисования» (`BIND_RENDER_TARGET`), число мипов. Читается геттерами контекста одинаково для своего и чужого. Хэши —
  тенью для своего, поиском хэша по объекту шейдера (как перепись рисований) для чужого. Первое рисование формы
  сохраняет свои аргументы (`DrawArgs`) и порядковый номер в листе.
- **Вне окна**, свой контекст: только если хэш VS — `B10B032B…` или `C4B4B334…`. Тогда форма с листом «вне узла».
- Формы лежат в таблице на 256 мест: ключ — хэш полей формы, место занимается CAS, счёт атомарный, поля пишет
  занявший. Переполнение только считается.
- *Цена:* в окне — несколько сотен рисований в секунду с геттерами. Вне окна — одно сравнение хэша на рисование. С
  выключенным ключом — одна проверка флага.

### 6. Где копится: перепись при смене и сводка в кадровом потоке

- Кадровый поток ведёт «картину части» по виду: есть ли часть в записи, число сеток, по каждой записи прохода (номер
  материала, три маски видов, листы), итог. Адресов сеток в картине нет: игра пересоздаёт их каждые несколько секунд
  (`.20`). При смене — чтение части и перепись элементов, не чаще раза в 5 с на вид, последняя отложенная держится.
- «Картина рисований» по виду и месту — набор ключей форм. При смене — перепись форм, по листам, до 16 строк.
- Раз в 30 с — сводка: чтения части по итогам и месту; рисования узла по листам, месту, своему и чужому контексту;
  формы «вне узла»; переполнения. «HUD-часть ещё не узнана» и «в узле не было рисований» — отдельными строками.

### 7. Сторожа HUD-части на слотах 2 и 3

Сторож ворот и выбор его цели (`gateWatchTarget`, вторая маска G4) убираются. Когда часть узнана, кадровый поток
ставит слот 2 на `part+0x10` (адрес массива сеток, 8 байт) и слот 3 на `part+0x08` (число сеток, 8 байт). Обработчик
пишет значение и место. Таблица мест, цепочка вызовов, предохранитель 100 000 за 30 с, строки «watch
on/off/moves», повторная постановка на новые потоки при смене «на ногах» — механика `.16`–`.20`. Имена:
`hud part meshes` и `hud part mesh count`.
- Сторожа снимаются со строкой, если части нет в записи 2 с, пока узел HUD рисуется. При новой части в
  кинотеатре они переставляются.
- *Почему два слота:* пересоздание сеток меняет адрес массива, а очистка части — число. Писатели могут быть разными.
- *Почему не по ссылкам в Ghidra:* поля `+0x08`/`+0x10` — у обычного контейнера, ссылок на такие смещения тысячи.

### 8. Какие исходы различает прогулка

| Исход | Признак в логе | Дальше |
|---|---|---|
| R1 — часть в стерео пуста | часть в записи, 0 сеток или 0 записей | писатель из строки сторожа в кинотеатре; статика: почему в стерео он не зовётся |
| R2 — `_HUD` только для другого вида | у материалов части `0x8` для вида ≠ вида набора | кто строит проходы материала по видам (`mat+0xB8`) |
| R3 — сетки без прохода `_HUD` | сетки есть, ни у одного материала `0x8` ни для какого вида | куда идут эти сетки (листы их проходов) и чем стерео-HUD отличается |
| R4 — части нет в записи | «части нет в записи», на её месте другой адрес | перепись элементов: где теперь HUD (счёты `_HUD` по элементам) |
| R5 — зонд читает не то | в кинотеатре итог части не «`_HUD` для вида набора» | исправить разбор, ещё круг |
| T1 — лист `_HUD` = скрытые панели | у рисований листа 39 в кинотеатре текстура-цель рисования размера панели (2008x1206, 2304x1984, 1800x1600) | панели в стерео уже есть: чинить сетки или класть панели самим по месту сеток |
| T2 — у листа `_HUD` свои текстуры | текстуры листа 39 — не цели рисования или не размера панелей | HUD — своя геометрия; панели — у листов 37/38 |
| T3 — рисования не в узле | 0 рисований в окне; формы `B10B032B`/`C4B4B334` вне узла | текстуры из форм «вне узла»; привязка к листу — статикой `vt[0x38]` |

## Risks / Trade-offs

- [Игра рисует узел на чужом (отложенном) контексте] → окно ловит и чужой контекст по потоку, форма читается
  геттерами, признак «чужой» в строке.
- [Игра рисует листы не в этом вызове, а позже] → исход T3 виден по нулю в окне и по формам «вне узла».
- [Начало `0x592090` нельзя перехватить (не 16 переносимых байтов)] → проверить при реализации (задача 2.1). Запасной
  путь — перехват `0x594EF0`, она вторая на листе. Тогда рисования внутри `0x592090` попадут к прошлому листу. По
  декомпиляции там только константы и камера, рисований нет.
- [Чтение всех материалов по 16 видам тяжёлое] → не больше 1024 материалов, раз в секунду на вид, вместе с обходом.
  Предел — константа.
- [Сторож на освобождённой памяти] → снятие по пропаже части на 2 с и предохранитель.
- [Новый вызов в пути рисований EDVR] → одна встроенная проверка флага, пока ключ выключен. Остальная работа — в
  зонде.

## Migration Plan

- Сборка `v0.19.1-edvronfoot.21`, установка `install_edvr.py`. В живом `edvr.ini` через Edit `on_foot_hud_probe = 1` на
  одну прогулку, после разбора — обратно 0.
- Откат — переустановка `.20` (`install_edvr.py` с тегом прошлой сборки). Правка меток и остальной EDVR не меняются.

## Open Questions

- Сколько форм рисований у узла на деле и хватит ли 256 мест — покажет первая перепись (число переполнений). Если
  не хватит, предел поднимается правкой константы.
